# Cerberus — бэклог идей (не реализовано, для обсуждения позже)

Собирается по ходу наблюдения за paper run. Ничего отсюда не внедряется
без отдельного запроса — это просто накопление идей на будущее, когда
перейдём к вопросу "как сделать чтобы работало автоматически на сервере
с нормальным дашбордом".

## 1. Автономность / отказоустойчивость процесса

- Сейчас процесс запускается вручную через `nohup ... &` — если Mac уйдёт
  в сон, перезагрузится, или процесс упадёт по необработанному исключению,
  никто не узнает и прогон просто остановится. Нужен супервизор:
  - Локально (пока на Mac): launchd job (аналог systemd на macOS) с
    `KeepAlive=true`, чтобы процесс автоматически поднимался после краша
    или перезагрузки.
  - На будущем сервере: systemd unit с `Restart=on-failure` +
    `RestartSec=` (не спамить рестартами при повторяющемся краше — нужен
    backoff или `StartLimitBurst`).
- Нужен heartbeat/watchdog: если `paper_run.log` не обновлялся N минут —
  алерт (Telegram токен уже есть в .env, notify.py уже существует в
  верхнеуровневой папке Cerberus — можно переиспользовать).
- Graceful shutdown: сейчас `kill` — просто SIGTERM. Нужно проверить, что
  cerberustest.py перехватывает SIGTERM и корректно закрывает websocket/db
  соединения, а не просто умирает на середине транзакции.

## 2. Мониторинг / алертинг

- dashboard.py уже существует (добавлен в сегодняшнем коммите с Windows) —
  read-only монитор БД+логов+процесса. Стоит:
  - Добавить автообновление (сейчас, видимо, разовый снимок — проверить).
  - Добавить алерт в Telegram при: kill_switch сработал, LEGGED_RISK
    произошёл, процесс не отвечает >N минут, rejection_reason
    концентрация >90% на одной причине (сигнал что фильтры не work).
- Метрика "near-miss": теперь что edge_net_pct пишется даже для FILTERED
  строк, можно построить live-график "насколько близко к порогу" — это
  прямой ответ на вопрос "движемся ли в сторону прибыльности".

## 3. Деплой на сервер (когда будем к этому готовы)

Варианты, не решено какой:
- **Простой VPS** (Hetzner/DigitalOcean, $5-10/мес) + systemd + cron для
  ротации логов. Плюсы: дёшево, полный контроль. Минусы: сам себе DevOps.
- **Docker-контейнер** на том же VPS — проще переносить между машинами
  (Mac ↔ сервер ↔ другой сервер), проще откатывать версии. Стоит сделать
  Dockerfile когда/если решим деплоить.
- Нужно решить: держать .env секреты (Telegram токен, в будущем
  POLYMARKET_PK для live) через переменные окружения хоста / secret
  manager, не коммитить и не хранить в открытом виде на сервере без
  шифрования диска.
- Часовой пояс сервера vs логики (сейчас всё в UTC внутри кода,
  таймстемпы ts_ms — проверить что нет мест с local time, которые
  поедут при переносе на сервер в другом поясе).

## 4. Дашборд (когда будем делать "нормальный")

Идеи, что должно быть на дашборде (сверх текущего dashboard.py):
- Live-график edge_net_pct по rejection_reason во времени (теперь что
  данные не NULL) — визуально видно "движется к профиту или нет".
- Разбивка по рынкам: какие рынки чаще дают близкий к порогу edge.
- PnL curve (симулированный, пока в paper-режиме) с разбивкой FOK/MAKER.
- Статус kill-switch / cooldowns / daily_loss_limit в реальном времени.
- История go-live критериев (чеклист из profitability_judge_panel_20260702.md)
  с прогресс-баром — сколько из 10 критериев выполнено.
- Технологически: раз БД — sqlite, можно поднять что-то лёгкое
  (Streamlit/Grafana+sqlite-datasource/самописный FastAPI+HTMX) —
  не решено, зависит от того, где будет жить (локально vs сервер, нужен
  ли доступ с телефона).

## 5. Прочие наблюдения по ходу работы (не срочно)

- risk_haircut в `evaluate_opportunity` (core.py) применяется к одному
  notional, но edge_net_pct нормализуется на notional*2 — по факту это
  вдвое снижает эффективную ставку haircut относительно того, что
  подразумевают имена параметров (slippage 0.5% + legged risk 0.3% на
  ногу). Второстепенный эффект, не главная причина текущих отказов, но
  стоит поправить при следующей калибровке порогов.
- Тесты test_market_discovery.py (test_filter_rejects_markets_too_far_in_future,
  test_filter_rejects_high_volume) утверждают старые пороги (30 дней,
  15000 volume), не совпадающие с фактическими константами в коде (90
  дней, 2 000 000). Тесты нужно обновить под актуальные пороги — сейчас
  falsely failing, но не блокируют работу.
- test_watcher_loop.py — 7 тестов падают на `FakeWS.recv` (мок не
  реализует нужный метод) — pre-existing, не связано с сегодняшними
  правками, но стоит когда-нибудь почистить.
